# 前端性能监控平台：面试讲解

## 一分钟项目介绍

这是一个前端性能监控平台，包含浏览器监控 SDK、Egg.js 数据服务和 React 可视化后台。SDK 基于 Web Vitals 与 Performance API 采集页面性能，同时监听 JavaScript 异常、资源加载失败、Promise 异常以及 XHR/Fetch 请求。数据批量上报后由服务端写入 Kafka 异步处理，监控明细存入 Elasticsearch，应用和用户数据存入 MySQL，实时统计使用 Redis 缓存，最后在 React 和 ECharts 后台中进行查询与展示。

## 建议职责表述

- 完善 XHR/Fetch 请求拦截与批量上报逻辑，降低监控请求对业务页面的影响
- 使用 React、TypeScript 和 ECharts 开发性能、异常、流量及接口分析页面
- 联调 Egg.js 数据接口，理解 Kafka、Elasticsearch、MySQL 和 Redis 的数据链路
- 使用 Docker Compose 搭建本地依赖环境，完成系统部署和功能验证

只保留自己确实完成并能解释的职责，不使用未经压测的数据量和性能提升比例。

## 核心数据链路

1. SDK 初始化后注册性能、错误、请求、路由和点击监听器。
2. 采集结果进入内存队列，并补充 appId、用户标识、页面地址和时间戳。
3. 队列达到 cacheMax 时批量上报，减少请求次数。
4. Egg.js 接口校验并接收数据，然后交给 Kafka 异步处理。
5. 消费者按数据类型写入 Elasticsearch，并更新 Redis 中的实时统计。
6. React 管理后台调用查询接口，使用 ECharts 展示趋势和 Top 数据。

## 高频追问

### 为什么要批量上报？

逐条上报会产生大量网络请求并占用浏览器连接。SDK 先把数据放入内存队列，达到阈值后合并发送，可以减少请求数量。页面卸载时还需要处理队列中的剩余数据。

### 如何避免监控自己的上报接口？

在请求拦截器中识别上报地址或添加内部请求标记，命中后直接跳过采集，避免形成“上报请求又触发上报”的递归循环。

### 如何捕获三类前端错误？

- `window` 的 `error` 事件捕获运行时错误
- 捕获阶段的 `error` 事件识别图片、脚本、样式等资源加载失败
- `unhandledrejection` 监听未处理的 Promise 拒绝

### 为什么使用 Elasticsearch？

监控明细字段多、写入量大，并且需要按时间、页面、错误类型等条件检索和聚合。Elasticsearch 比关系型数据库更适合这类日志查询；MySQL 则继续保存用户、应用等结构稳定且需要事务的数据。

### Kafka 的作用是什么？

Kafka 把接收请求与后续存储解耦。上报接口可以快速响应，消费者再异步完成分类、聚合和持久化；流量高峰时消息队列还能缓冲瞬时写入压力。

### SDK 如何降低对业务性能的影响？

- 只注册必要的全局监听器
- 通过批量上报减少网络请求
- 使用 Performance API，避免主动轮询
- 控制采集字段和资源明细数量
- 上报失败不阻塞业务逻辑

### FID 为什么需要注意版本问题？

FID 已逐步被 INP 取代。当前项目依赖的 Web Vitals 版本仍采集 FID；面试时应说明生产升级会补充 INP，并根据浏览器兼容性保留历史指标。
